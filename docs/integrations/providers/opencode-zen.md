# OpenCode Zen (`openCodeZen`) - and why "OpenCode Go" isn't a separate provider

**Sourcing note:** `opencode.ai` was not directly fetchable from this session's sandbox (egress-blocked). Facts below come from web search corroborated against a GitHub bug-fix issue in the upstream `opencode` repo that quotes the literal base-URL string, and a mirror of the official docs (`github.com/mudrii/opencode-docs`).

## What these two names actually are (verified, not assumed)

The real, current `opencode` project (a terminal-based AI coding agent, `github.com/anomalyco/opencode` - renamed from `sst/opencode`; a separate, unrelated `opencode-ai/opencode` repo exists and is a common source of confusion) ships two first-party, real, callable services, both under `opencode.ai`:

- **OpenCode Zen**: a genuine pay-as-you-go model gateway, in beta. A curated, benchmarked catalog of models (OpenAI, Anthropic, Google, plus several Chinese-lab models) reachable through one gateway after adding billing.
- **OpenCode Go**: a **$10/month subscription tier** (a specific, subscription-gated slice of the *same* gateway infrastructure) giving stable, higher-rate-limit access to a curated set of open-weight coding models, hosted at `opencode.ai/zen/go/v1/...` - i.e. the same protocol as Zen, under a different base path a subscriber's key is scoped to.

Because Go is the same wire protocol as Zen through a different URL, Vader implements one provider (`openCodeZen`) rather than two - a Go subscriber can point the `endpoint` setting at their Go URL instead of Zen's default and everything else (auth, request/response shape) works identically.

## What Vader's integration covers, and what it deliberately doesn't

- **Endpoint (Vader's default)**: `https://opencode.ai/zen/v1` (OpenAI-shaped chat completions). **Real, confirmed base-URL family** (corroborated by a GitHub issue that quotes the literal string): OpenAI-format models at `/zen/v1/chat/completions` (and `/zen/v1/responses`); Anthropic-format models at `/zen/v1/messages`; Gemini at `/zen/v1/models/<model>`; model catalog at `/zen/v1/models`.
- **Auth**: `Authorization: Bearer <key>`, obtained from `opencode.ai/auth` after adding billing.
- **What Vader reaches**: only the OpenAI-shaped `/zen/v1/chat/completions` surface, via the same `newOpenAICompatibleSDK`/`_sendOpenAICompatibleChat` path every other OpenAI-compatible provider uses. This covers OpenAI-family models and (per the gateway's own description) most third-party/Chinese-lab models it proxies, since those are generally exposed in OpenAI shape.
- **What Vader does NOT reach, and why**: per Zen's own documented architecture, Anthropic and Gemini models are proxied through **those vendors' native wire formats** (`/v1/messages`, `/v1/models/<id>`), not flattened into one OpenAI schema. Reaching them would require per-model-family request shaping specific to this one gateway - a distinct code path, not a config toggle. This is a stated, precise scope boundary, not a silent gap: if a user selects an Anthropic- or Gemini-family model by name through this provider, the request will be sent in OpenAI shape and will likely fail against Zen's native-format endpoint for that model family. Building the additional two branches is a concrete, bounded follow-up if full-catalog coverage is needed.
- **Model catalog**: intentionally empty by default (`defaultModelsOfProvider.openCodeZen = []`) since the catalog is explicitly beta and volatile (~40+ models on Zen, ~9-12 on Go, roster changing) - exactly the same treatment Vader already gives `openAICompatible` (no fixed catalog, `modelOptionsFallback` handles anything the user types). The user adds the exact model id shown in their own Zen/Go console.
- **Streaming/tool-calling/vision**: not confirmed per-model from primary docs (the capability matrix wasn't independently found); since Zen proxies the same underlying frontier/open models Vader already knows about by name pattern, `getModelCapabilities`'s fallback and `modelSupportsVision`'s generic pattern matching (which checks the same vision-model-name patterns used for every other provider) apply reasonably, but this is explicitly a best-effort inference for this specific gateway, not a confirmed-per-model fact.
- **Branding**: a real official brand page exists at `opencode.ai/brand` (stated to host SVG/PNG/WEBP logos with light/dark variants) but could not be fetched directly from this sandbox to vendor a real asset - see the marketplace/branding section of the production-hardening report for the current state of provider icon assets generally.
