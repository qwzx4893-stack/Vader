# Windows development validation

Acceptance: run the current branch's source in real Windows Electron, preserve existing regression gates, exercise all selected existing real-app scenarios, record resource/process evidence automatically, retain failures and artifacts, and keep vendor connectivity claims separate from scripted model behavior. A missing result, skip, failed check, timeout, monitoring error, sustained resource-limit breach or surviving observed child makes the development supervisor fail. A green badge is not proof that every possible feature is correct.

`.github/workflows/windows-dev-validation.yml` runs on the `test/windows-dev-validation` branch. A push trigger works before the workflow exists on main; manual dispatch becomes available after it is on the default branch. It installs native dependencies, builds the renderer/runtime bundles, type-checks and compiles the development tree, fetches Electron and built-in extensions, then runs startup smoke, the existing scripted real-app suite and the real-model suite serially. It does not minify, package, install, publish, update branch protection, or merge. The separate PR CI workflow runs source regressions and browser harnesses; those harnesses are not the full app.

The supervisor is `src/vs/workbench/contrib/vader/test/devValidation/run.mjs`. `VADER_EXE` points to `.build/electron/<product.nameShort>.exe`, `VSCODE_DEV=1` and `.` is passed as the Electron application path. Test homes, profiles and workspaces are disposable, not copies of user data. The public MCP fixture runs a real local stdio server. The scripted model server supplies deterministic protocol responses; this is explicitly not a real external model. The live step uses `OPENROUTER_API_KEY` from Actions secrets and the repository variable `VADER_TEST_MODEL` (default `poolside/laguna-s-2.1:free`). Missing credentials fail that step; unavailable models and rate limits remain real failures. No local agent account credentials are uploaded. Account/OAuth approval, other vendor accounts, installer/updater behavior, GPU/driver differences and physical-machine performance remain outside this run.

The runtime includes the two actual local search models prepared from the locked manifests, and the native worker integration checks normalized, nonzero vectors from both tiers. A real-app indexed-search scenario exercises IPC and actual project content. These checks are not a retrieval-quality benchmark. Dependency caches include native modules and are keyed by runtime/lockfiles/install scripts; application output is always compiled fresh.

The observer samples kernel-owned processes approximately every five seconds, with Windows CIM role enrichment and no overlapping queries. It records process identities (PID + creation time), roles, private memory, working set, handles, CPU and I/O deltas, and reports children left after shutdown. It never exports command lines or environment variables. CPU 100% means one core. The tree includes the driver and fixture servers as well as the app; per-process rows allow separation. Working sets share pages; I/O includes pipes/devices and is not a network-byte measurement. Per-process snapshots can miss short-lived processes; this is not a kernel trace or proof of absence of leaks. The initial safety limit is 6000 MiB private tree memory for three consecutive samples; it is a runaway guard, not a performance target. Peaks and trends must still be reviewed against user-machine expectations. Window/readiness timeouts and scenario assertions detect visible hangs; no claim of monitoring every backend operation is made.

Ownership in the supervisor is enforced with an unnamed Windows Job Object, not inferred from sampled parent PIDs. A standard-library Python helper creates the driver suspended, assigns it before resuming, disallows breakaway and uses kill-on-close. Kernel membership retains living descendants after launcher exit; cumulative job CPU/I/O includes completed members. CIM only enriches per-process roles. Cleanup records leaks before termination, verifies empty membership, and keeps any failure sticky. The helper uses explicit inherited handles and fails closed if containment cannot be established. This contains CreateProcess descendants (including nested jobs); it is not a security sandbox for processes created through unrelated services/WMI. Per-process memory snapshots can still miss completed processes. The ancestry-only observer remains for compatibility fixtures and is not the supervisor's ownership mechanism.

Artifacts contain scenario results, screenshots, diagnostic logs, `resources.jsonl`, a monitoring verdict and the checked-out commit. Temporary profile/home stores are not uploaded. The live secret is removed from diagnostic text before upload, and the supervisor redacts it from streamed console logs. Screenshots are test-owned content; do not enter personal account credentials into these CI profiles. Artifacts retain seven days. Upload runs after failure, but runner termination/cancellation may prevent complete diagnostics.

Real-app scenario screenshots mask API-key/password inputs and any rendered text matching the live secret, without modifying product behavior. Smoke/scripted artifacts are uploaded before the longer subsequent phases, after sanitization, so startup failures can be inspected immediately. A fresh-profile smoke explicitly waits for onboarding instead of racing a briefly interactive shell before the setup contribution mounts.

The shared real-app launcher also selects modern versus classic readiness according to the journey; hidden classic titlebars cannot establish modern-window readiness. MCP fixtures use the development product directory when `VSCODE_DEV` is set. A manual update check in a source build performs only the read-only GitHub release comparison; development background/native updating remains disabled. Live coding attempts retain separate file/transcript JSON evidence before the next attempt resets its fixtures. Their on-disk grades and error checks remain mandatory.

Native dependency cache keys include participating package manifests, lockfiles and nested `.npmrc` runtime settings. Cache restoration still runs dependency installation, and does not restore application output. Attempted diagnostic uploads fail if their evidence directory is empty; missing evidence is not a successful artifact upload. The Windows job gate includes isolated exit-race API fixtures as well as real kernel/process tests; the fixtures alone do not establish containment.

Installer packaging is a separate manual `Windows Build` dispatch. Main-branch dependency/source merges do not implicitly package a Windows installer. Publishing additionally requires that dispatch's explicit `publish` input; development validation never dispatches it or publishes releases. Packaged `Windows E2E` is also manual, so a source-only merge does not present a test of an older installer as verification of the new source.

Local gate verification: `node src/vs/workbench/contrib/vader/test/devValidationE2E.mjs`. This uses isolated fixtures for PID reuse, unrelated processes, CPU/I/O deltas, malformed measurements, intentionally failing checks, false totals, missing results, timeouts, observer failures, resource breaches and leaks. It does not establish Windows app startup. Actual run URLs and outcomes must be reported after Actions executes, with skipped/uncovered features explicit. Merge is conditional on reviewed CI/runtime results; this workflow does not auto-merge.

`node src/vs/workbench/contrib/vader/test/devValidationJobE2E.mjs` separately exercises actual Windows containment, lost ancestry, breakaway rejection, nested jobs, helper/caller death and cleanup. The required scenario inventory rejects partial/duplicate results and passing rows without assertions. Live turns must have no provider errors and produce their requested content/files; idle alone is not success. Cancellation uses a nonrepeating stream so it tests Stop rather than the separate repeated-output guard. Startup polling uses direct CDP evaluation under the workbench CSP (without disabling Trusted Types), and requires controls that actually receive a hit test, including the first-run language selector.
