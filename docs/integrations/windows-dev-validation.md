# Windows development validation

Acceptance: run the current branch's source in real Windows Electron, preserve existing regression gates, exercise all selected existing real-app scenarios, record resource/process evidence automatically, retain failures and artifacts, and keep vendor connectivity claims separate from scripted model behavior. A missing result, skip, failed check, timeout, monitoring error, sustained resource-limit breach or surviving observed child makes the development supervisor fail. A green badge is not proof that every possible feature is correct.

`.github/workflows/windows-dev-validation.yml` runs on the `test/windows-dev-validation` branch. A push trigger works before the workflow exists on main; manual dispatch becomes available after it is on the default branch. It installs native dependencies, builds the renderer/runtime bundles, type-checks and compiles the development tree, fetches Electron and built-in extensions, then runs startup smoke, the existing scripted real-app suite and the real-model suite serially. It does not minify, package, install, publish, update branch protection, or merge. The separate PR CI workflow runs source regressions and browser harnesses; those harnesses are not the full app.

The supervisor is `src/vs/workbench/contrib/vader/test/devValidation/run.mjs`. `VADER_EXE` points to `.build/electron/<product.nameShort>.exe`, `VSCODE_DEV=1` and `.` is passed as the Electron application path. Test homes, profiles and workspaces are disposable, not copies of user data. The public MCP fixture runs a real local stdio server. The scripted model server supplies deterministic protocol responses; this is explicitly not a real external model. The live step uses `OPENROUTER_API_KEY` from Actions secrets and the repository variable `VADER_TEST_MODEL` (default `poolside/laguna-s-2.1:free`). Missing credentials fail that step; unavailable models and rate limits remain real failures. No local agent account credentials are uploaded. Account/OAuth approval, other vendor accounts, installer/updater behavior, GPU/driver differences and physical-machine performance remain outside this run.

The observer samples Windows CIM every approximately five seconds, without overlapping queries. It records owned process identities (PID + creation time), process roles, private memory, working set, handles, CPU and I/O deltas, and reports observed children left after shutdown. It never exports command lines or environment variables. CPU 100% means one core. The tree includes the driver and fixture servers as well as the app; per-process rows allow separation. Working sets share pages; I/O includes pipes/devices and is not a network-byte measurement. Sampling can miss short-lived processes; this is not a kernel trace or proof of absence of leaks. The initial safety limit is 6000 MiB private tree memory for three consecutive samples; it is a runaway guard, not a performance target. Peaks and trends must still be reviewed against user-machine expectations. Window/readiness timeouts and scenario assertions detect visible hangs; no claim of monitoring every backend operation is made.

Artifacts contain scenario results, screenshots, diagnostic logs, `resources.jsonl`, a monitoring verdict and the checked-out commit. Temporary profile/home stores are not uploaded. The live secret is removed from diagnostic text before upload, and the supervisor redacts it from streamed console logs. Screenshots are test-owned content; do not enter personal account credentials into these CI profiles. Artifacts retain seven days. Upload runs after failure, but runner termination/cancellation may prevent complete diagnostics.

Local gate verification: `node src/vs/workbench/contrib/vader/test/devValidationE2E.mjs`. This uses isolated fixtures for PID reuse, unrelated processes, CPU/I/O deltas, malformed measurements, intentionally failing checks, false totals, missing results, timeouts, observer failures, resource breaches and leaks. It does not establish Windows app startup. Actual run URLs and outcomes must be reported after Actions executes, with skipped/uncovered features explicit. Merge is conditional on reviewed CI/runtime results; this workflow does not auto-merge.
